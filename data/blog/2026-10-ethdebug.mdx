_Compilers can now better explain their bytecode to tools. This post covers what
that looks like today, how you can build on it, and what's coming next for the
maturing debugging data format._

The **ethdebug format** is an open specification for compilers to use in
structuring their debug output. Like DWARF for traditional computing, but
designed for the quirks of smart contract languages, it seeks to reduce the
cost to understand the blockchain. **ethdebug** is an Argot Collective
project, and this post is its first introduction on this blog.

Today, the format is real: the compilers **solc**, **Fe** and **Solar** produce
data in it, and tools are starting to consume it. Walnut's **soldb** reads it,
and Runtime Verification's **Simbolik** uses it internally. We are proud of the
work on both sides: compilers, who must produce this data, and debuggers and
other tools, who consume it.

While this tooling continues to improve, there is enough here to show what this
new information makes possible: tools can stop guessing what the compiler
meant.

## Tools have always worked backwards

Smart contracts are written in languages for humans to read, but they run as
machine code and keep their state in the terms of the Ethereum Virtual Machine.
The compiler serves both sides: it keeps the human's abstractions clear, and it
makes the machine code cheap to run, because computation on the EVM is
expensive. Compilers have become very good at this. But with modern optimizers,
the raw state of the machine can be very hard to decipher, even for experts.

Throughout Ethereum's history, people have needed to see through these
compiler-managed internals. Public blockchains can control significant value,
so it is essential to understand how a contract fails: before, during
development, and after, in case of a security incident. Many independent groups
have built tools with essentially the same goal: undo the compiler's tricks and
recover the human abstractions from the machine.

Compilers have given these tools enough information to succeed, but only with
guesswork: rules learned by watching the compiler, and special cases for each
version, because compiler internals change from release to release. Each new
language, and each new compiler for a language, is a new challenge.

Take a small example, which the rest of this post uses too: a multiplayer game
where players join and make moves that may earn them points. This is what a
development tool sees when it looks at the game's state in the middle of a
transaction:

Without this data, a tool has to guess, and usually the guess is right. Tool
authors learn each compiler's rules by watching what it does: where Solidity
puts a mapping's entries, how it packs small values into one slot, how it lays
out a string. They build those rules into their tools, and most of the time the
tools read the right bytes.

The trouble starts when a rule doesn't fit. A tool can't tell when it has met a
case its rules never covered. It applies the rule it knows, and the answer it
gets looks just as plausible as a correct one. And getting every rule right is
hard.

Even within one language, designing software to use clear abstractions means
structuring data in nested containers. To find Alice's score in the game, a tool
hashes her address with the mapping's slot (using keccak, Ethereum's standard
hash function) to find her record, then picks her score out of six small fields
packed into that one slot. Her name sits in the next slot, but not as plain
text: the characters start at one end, their length is tucked into the other,
and the bytes between mean nothing. Each layer has its own rule, and a tool that
gets any one of them wrong reads the wrong bytes.

<EthdebugFigure scene="pitfall-nesting" size="wide">
  Alice's record, as the compiler's data describes it: six fields packed into
  one slot, then her name, with its characters at one end of the next slot
  and its length at the other. The grey rows are the ones a tool reads on the
  way to finding it.
</EthdebugFigure>

Then a tool has to do it all again for the next language. Sometimes the rules
match up, and sometimes they are off in subtle ways. Vyper also finds a
mapping's entry by hashing the key together with the mapping's slot, but it
hashes them in the other order: slot first, then key. Its slot numbers differ
too, because Vyper reserves room for an array's or a string's full capacity, so
the game's players mapping lands at slot 108 instead of slot 3. A tool that
applies Solidity's rule to Vyper's storage computes a slot that looks just as
valid, finds it empty, and reports that Alice's score is 0. Here is the same
game compiled with Vyper, read the way a Solidity tool would read it:

<EthdebugFigure scene="pitfall-compiler" size="wide">
  The same storage, read two ways. Solidity's rule hashes Alice's address
  before the slot and lands on an empty slot, so her score reads 0. Vyper's
  layout hashes the slot first and finds her real score: 30.
</EthdebugFigure>
