_Compilers can now better explain their bytecode to tools. This post covers what
that looks like today, how you can build on it, and what's coming next for the
maturing debugging data format._

The [**ethdebug format**](https://ethdebug.github.io/format/) is an open
specification for compilers to use in structuring their debug output. Like
[DWARF](https://dwarfstd.org/) for traditional computing, but designed for the
quirks of smart contract languages, it seeks to reduce the cost to understand
the blockchain. **ethdebug** is an [Argot Collective](https://www.argot.org/)
project, and this post is its first introduction on this blog.

Today, the format is real: the compilers [**solc**](https://soliditylang.org/),
[**Fe**](https://fe-lang.org/) and
[**Solar**](https://github.com/paradigmxyz/solar) produce data in it, and tools
are starting to consume it. [Walnut](https://www.walnut.dev/)'s
[**soldb**](https://github.com/walnuthq/soldb) reads it, and [Runtime
Verification](https://runtimeverification.com/)'s
[**Simbolik**](https://marketplace.visualstudio.com/items?itemName=runtimeverification.simbolik)
uses it internally. We are proud of the work on both sides: compilers, who must
produce this data, and debuggers and other tools, who consume it.

While this tooling continues to improve, there is enough here to show what this
new information makes possible: tools can stop guessing what the compiler
meant.

## Tools have always worked backwards

Smart contracts are written in languages for humans to read, but they run as
machine code and keep their state in the terms of the Ethereum Virtual Machine.
The compiler serves both sides: it keeps the human's abstractions clear, and it
makes the machine code cheap to run, because computation on the EVM is
expensive. Compilers have become very good at this. But with modern optimizers,
the raw state of the machine can be very hard to decipher, even for experts.

Throughout Ethereum's history, people have needed to see through these
compiler-managed internals. Public blockchains can control significant value,
so it is essential to understand how a contract fails: before, during
development, and after, in case of a security incident. Many independent groups
have built tools with essentially the same goal: undo the compiler's tricks and
recover the human abstractions from the machine.

Compilers have given these tools enough information to succeed, but only with
guesswork: rules learned by watching the compiler, and special cases for each
version, because compiler internals change from release to release. Each new
language, and each new compiler for a language, is a new challenge.

Take a small example, which the rest of this post uses too: a multiplayer game
where players join and make moves that may earn them points. This is what a
development tool sees when it looks at the game's state in the middle of a
transaction:

Without good debug data, a tool has to guess. Usually the guess is right; tool
authors learn each compiler's rules by observing its behavior: [where Solidity
puts mapping
entries](https://docs.soliditylang.org/en/latest/internals/layout_in_storage.html),
how it saves gas by packing small values into one slot, how it lays out a
string. They copy their understanding of these rules into their tools.

It is tedious, unending work to manage these compiler rules this way. Compiler
behavior changes with new versions, optimizers make rules unpredictable, and
none of the old rules ever go away: contracts on chain live forever, so a tool
must keep reading the output of every compiler version anyone ever deployed
with. The special cases pile up, and each change gets harder to make. In
practice, tools fall behind: they support some compiler versions and not others,
one language and not the next, and often not the optimized code that actually
runs on mainnet.

Sometimes, the guess is wrong. When it is, _nothing warns the tool_. Wrong
answers are just as plausible as right answers.

To illustrate the kind of diligence involved: designing software with clear
abstractions often means structuring data in nested containers, like a record
inside a mapping. The compiler preserves that nesting; every container still
exists in storage, holding the same things. But it encodes the nesting in a form
that looks nothing like the source: a record's location becomes a hash, and
separate fields share a single word.

For example, to find Alice's score in this smart contract game, a tool hashes
her address with the mapping's slot (using keccak, Ethereum's standard hash
function) to find her player record, then picks her score out of six small
fields packed into that one slot. Her name sits in the next slot, but not as
plain text: the characters start at one end, their length is tucked into the
other, and the bytes in between are unused.

There are different rules for each type of data and each type of nesting, and a
tool that gets any one of them wrong reads the wrong bytes. Then, for the next
language, a tool has to do it all again. Sometimes the rules match up, and
sometimes they are off in subtle ways. [Vyper](https://vyperlang.org/), for
instance, also finds a mapping's entry by hashing the key together with the
mapping's slot, but it hashes them in the opposite order: slot first, then key.
Its slot numbers differ too because Vyper reserves room for an array's or a
string's full capacity: the game's `players` mapping lands at slot 108 instead
of slot 3. A tool that applies Solidity's rule to Vyper's storage computes a
slot that looks just as valid, finds it empty, and reports that Alice's score
is 0. Here is the same game compiled with Vyper, read the way a Solidity tool
would read it:

<EthdebugFigure scene="pitfall-compiler" size="narrow">
  The same storage, read two ways. Solidity's rule hashes Alice's address
  before the slot and lands on an empty slot, so her score reads 0. Vyper's
  layout hashes the slot first and finds her real score: 30.
</EthdebugFigure>

Nothing in the bytes says which rule is right, so the tool just shows a score of
0.

The ethdebug format moves the rule into the compiler's output. The compiler
already knows where it put every value, so it writes the rule down: for
`players`, hash the key with slot 3, or, for Vyper, slot 108 with the key. A
tool follows whatever rule it's given, so it reads Alice's 30 from Vyper's
storage without knowing anything about Vyper. The right side of the figure above
works exactly that way, from hand-written ethdebug data; the storage colors in
the first figure came the same way, from solc's own output.

## Three compilers produce ethdebug data today

solc writes it behind an experimental flag. Today that covers which piece of
source each instruction came from: the same information as solc's older source
maps, in a simpler shape. Walnut, the team building solc's support, is adding
more in stages; their working branch already lists where every state variable
lives.

Fe, a separate contract language and another Argot project, writes ethdebug as
its only debug output, and it works with the optimizer on. Solar, a second
Solidity compiler from [Paradigm](https://www.paradigm.xyz/), writes it on its
main branch, also with the optimizer on, and its bytecode is the same with or
without the debug data.

Walnut also makes soldb, a debugger. It was written for Solidity. But because it
reads ethdebug, it can step through a Fe contract too, with no changes to soldb
itself; we only had to pass it Fe's files. The figure below runs soldb right in
this page, on the same game transaction compiled both ways. Switch between
Solidity and Fe, and step through each.

<EthdebugFigure scene="real-debugger" size="narrow">
  soldb stepping one of the game's transactions, compiled from Solidity and
  from Fe.
</EthdebugFigure>

What soldb reads is simple. The format describes compiled code as [**ethdebug
programs**](https://ethdebug.github.io/format/spec/program). An ethdebug program
is one piece of bytecode that a compiler produced: a contract's deployed code,
or the code that creates it. For each program, the compiler lists the
instructions, in order. Each instruction gives its byte offset in the bytecode
and its operation (the opcode, plus any data pushed with it), and a [**ethdebug
context**](https://ethdebug.github.io/format/spec/program/context): what the
compiler knows to be true once that instruction has run.

The simplest kind of context, and the one every compiler emits today, says which
range of which source file the instruction came from. That is all soldb needed
to follow the source. Other kinds describe variables, function calls, and code
the optimizer moved or merged; we will come back to those.

Solidity and Fe write ethdebug programs in the same shape, so one reader handles
both. Point at an instruction below to see its entry.

<EthdebugFigure scene="program-xray" size="text">
  Part of `play()`, as solc and Fe each wrote it: one entry per instruction,
  with its offset, its operation and its context. Pick an instruction to see its
  entry and the source its range points to; Fe adds a few fields of its own.
</EthdebugFigure>

That covers where the code came from. Finding where a value lives, for any type,
in any language, is the hard part. That's what ethdebug pointers are for.

## ethdebug pointers: the compiler states the rule, and any tool applies it

For each variable, the compiler writes a [**ethdebug
pointer**](https://ethdebug.github.io/format/spec/pointer): a description of
where the variable's bytes are, written as a recipe a tool can follow. An
ethdebug pointer names a location (storage, memory, the stack) and computes
positions from what is already there: read this slot, hash this key with it,
step to the next slot. Recipes for shapes the compiler uses again and again,
like a mapping or a string, are written once as templates and reused.

The figure below follows the compiler's ethdebug pointer for `players`, from the
slot it starts at to every byte of every player's record. Press ▶ to step
through it. You can also select any other variable in the figure, such as
`playerList`, `motd` or one player's `score`, and step through the ethdebug
pointer that finds it.

<EthdebugFigure scene="pointer-walkthrough" size="wide" walkthrough>
  The compiler's ethdebug pointer for `players`, followed step by step: from
  slot 3, to each record at keccak(key, slot 3), to the six packed fields and
  each player's name. The panel shows the piece of the pointer each step uses.
</EthdebugFigure>

Nothing in those steps is specific to this game, or to Solidity. The keys came
from the game's list of players, but every rule after that came from the
compiler's data: where the mapping starts, how a key picks a record, how six
fields share one slot, and how a string tells its short form from its long one.
A tool that can follow an ethdebug pointer finds this data without knowing any
of those rules. The figure itself does exactly that, with our reference
implementation, the
[`@ethdebug/pointers`](https://www.npmjs.com/package/@ethdebug/pointers)
package.

An ethdebug pointer for the Vyper version of the game would hash the slot before
the key, start at slot 108, and give each field a slot of its own. The tool
following it wouldn't change.
